# Project Rules

Read and follow these rules before making any change in this repository.

## Purpose
This repository is a **caching course**. The user is learning caching from beginner to advanced, with Claude as the teacher.
- Each topic gets real backend code (the user learns from the code) and a portal page that explains how it works and lets the user run a live demo.
- The course is built **one level at a time**. Do not start the next level until the user asks for it.

## Project type
- .NET 10 ASP.NET Core MVC application.
- The backend is **API based**: all caching logic is exposed through API controllers.
- The **portal uses MVC Views** and exists for demonstration and explanation only. Portal pages call the API with `fetch`.
- Use **Swagger only** (Swashbuckle) for API documentation. Do not add Scalar, NSwag or Microsoft.AspNetCore.OpenApi. Portal controllers have `[ApiExplorerSettings(IgnoreApi = true)]` so they stay out of Swagger.
- Use **both EF Core and Dapper** for data access.
- Database is **SQLite** (`caching.db`). Tables are created only through **EF Core migrations**, which are applied automatically at startup.
- **Do not write any comments** anywhere: C#, Razor, JavaScript, CSS. EF Core generated migration files must also have their comments stripped (`// <auto-generated />`, `/// <inheritdoc />`, trailing `// ...` on pragmas).
- Keep the code as simple as possible.

## Layer rules
- **Core**: controllers only. API controllers depend on Business service interfaces and use DTOs. Portal controllers only return views. No business or database logic here.
- **Business**: all business and caching logic. Services go in `Service/Interface` and `Service/Implementation`. DTOs go in `Dto`. Entity/DTO mapping goes in `Mapper` (simple static extension methods, no AutoMapper). All cache keys are built in `Constant/CacheKeys.cs` using the format `levelN:entity:id`.
- **Infrastructure**: all database, Redis connection and external API logic. Repositories go in `Repository/Interface` and `Repository/Implementation`. Entities go in `Data/Entity`, the DbContext in `Data/DbContext`, migrations in `Data/Migrations`.
- Reference direction: `Core -> Business -> Infrastructure`. Never reference upward. Core only calls Business.
- Dependency registration: each library exposes extension methods in `DependencyInjection.cs` (`AddInfrastructure`, `AddBusiness`, `ApplyDatabaseMigrations`). `Program.cs` calls only the Business ones.
- Data access convention: Dapper for reads, EF Core for writes.
- Repository reads wait `Database:SimulatedDelayMs` (appsettings) to simulate a slow database so the effect of caching is visible.
- HTTP-level caching is configured in `Program.cs` because it belongs to the HTTP pipeline: `AddResponseCaching`/`UseResponseCaching`, `AddOutputCache` (policy `Products`, tag `products`)/`UseOutputCache` after `UseRouting`, and `UseStaticFiles` with `OnPrepareResponse` (versioned `?v=` files get `immutable`, others `no-cache`).
- The response caching middleware stores every `public` response app-wide. Endpoints whose demos must reach the controller or show browser-only caching use `private`.
- Level 2 demos detect cache hits with `IRequestCounter` (`api/level2/counters`): the counter only increases when the controller action really runs.

## Portal lesson page format
Every lesson view follows the same structure:
1. Title and one-sentence lead
2. Concept explanation in plain language (cards, flow diagrams with `.flow`, tables)
3. Live demo calling the API, with results, timings and an event log (`ICacheEventLog`, filtered by key prefix)
4. Numbered experiments for the user to run
5. Key takeaways and common mistakes (`.callout`)
6. "Read the code" list of the files to study
7. Link to the next lesson

## Redis
- Connection string key: `ConnectionStrings:Redis`, in StackExchange.Redis format (`host:port,user=...,password=...,abortConnect=false`), not the `redis://` URI format.
- By the user's explicit decision, the Redis Cloud connection string is stored in `src/Caching.Core/appsettings.json` and committed, even though the repository is public. The user knows the risk and will move it to a Render environment variable or user secrets later. Do not move or remove it unless the user asks.
- `AddInfrastructure` registers `IConnectionMultiplexer` and `AddStackExchangeRedisCache` only when the connection string is not empty. Redis features must handle Redis not being configured or not reachable.
- The Claude cloud sandbox cannot reach the Redis host, so Redis code cannot be tested live from there.

## Packages
- All Microsoft.* packages (EF Core, Extensions) must stay on version `10.0.x` (currently `10.0.15`). Version 11.x targets net11.0 and does not work on net10.0.
- EF Core tools: `dotnet tool install --global dotnet-ef --version 10.0.15`.
- Add a migration: `dotnet ef migrations add <Name> --project src/Caching.Infrastructure --startup-project src/Caching.Core --output-dir Data/Migrations`, then strip the generated comments.

## Running
`dotnet run --project src/Caching.Core` then open `http://localhost:5030` for the portal and `http://localhost:5030/swagger` for the API.

## Deployment
- Hosted on **Render** (free plan) using `Dockerfile` and the `render.yaml` blueprint. GitHub Pages cannot host this app because it needs a .NET server.
- Render builds from the branch named in `render.yaml` and redeploys automatically on every push to it.
- The container listens on port 10000 (`ASPNETCORE_HTTP_PORTS`). Render provides HTTPS.
- The SQLite file is recreated from migrations on each deploy or restart (Render's free disk is temporary). This is fine because the data is only demo data.
- The Redis connection string currently comes from `appsettings.json`. A `ConnectionStrings__Redis` environment variable in Render, if set, overrides it.
