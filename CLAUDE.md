# Project Rules

Read and follow these rules before making any change in this repository.

## Purpose
This repository is a **caching course**. The user is learning caching from beginner to advanced, with Claude as the teacher.
- Each topic gets real backend code (the user learns from the code) and a portal page that explains how it works and lets the user run a live demo.
- All seven levels are complete. For changes, keep each lesson self-contained and follow the lesson page format below.

## Course progress

|---|---|---|

Update this table when a level is finished.

## Project type
- .NET 10 ASP.NET Core MVC application.
- The backend is **API based**: all caching logic is exposed through API controllers.
- The **portal uses MVC Views** and exists for demonstration and explanation only. Portal pages call the API with `fetch`.
- Use **Swagger only** (Swashbuckle) for API documentation. Do not add Scalar, NSwag or Microsoft.AspNetCore.OpenApi. Portal controllers have `[ApiExplorerSettings(IgnoreApi = true)]` so they stay out of Swagger.
- Use **both EF Core and Dapper** for data access.
- Database is **SQLite** (`caching.db`). Tables are created only through **EF Core migrations**, which are applied automatically at startup.
- **Do not write any comments** anywhere: C#, Razor, JavaScript, CSS. EF Core generated migration files must also have their comments stripped (`// <auto-generated />`, `/// <inheritdoc />`, trailing `// ...` on pragmas).
- Keep the code as simple as possible.

## Layer rules
- **Core**: controllers only. API controllers depend on Business service interfaces and use DTOs. Portal controllers only return views. No business or database logic here.
- **Business**: all business and caching logic. Services go in `Service/Interface` and `Service/Implementation`. DTOs go in `Dto`. Entity/DTO mapping goes in `Mapper` (simple static extension methods, no AutoMapper). All cache keys are built in `Constant/CacheKeys.cs` using the format `levelN:entity:id`.
- **Infrastructure**: all database, Redis connection and external API logic. Repositories go in `Repository/Interface` and `Repository/Implementation`. Entities go in `Data/Entity`, the DbContext in `Data/DbContext`, migrations in `Data/Migrations`.
- Reference direction: `Core -> Business -> Infrastructure`. Never reference upward. Core only calls Business.
- Dependency registration: each library exposes extension methods in `DependencyInjection.cs` (`AddInfrastructure`, `AddBusiness`, `ApplyDatabaseMigrations`). `Program.cs` calls only the Business ones.
- Data access convention: Dapper for reads, EF Core for writes.
- Repository reads wait `Database:SimulatedDelayMs` (appsettings) to simulate a slow database so the effect of caching is visible.
- HTTP-level caching is configured in `Program.cs` because it belongs to the HTTP pipeline: `AddResponseCaching`/`UseResponseCaching`, `AddOutputCache` (policy `Products`, tag `products`)/`UseOutputCache` after `UseRouting`, and `UseStaticFiles` with `OnPrepareResponse` (versioned `?v=` files get `immutable`, others `no-cache`).
- The response caching middleware stores every `public` response app-wide. Endpoints whose demos must reach the controller or show browser-only caching use `private`.
- Level 3 strategies live in separate Business services (`CacheAsideService`, generic `ReadThroughCache<T>` with a loader set in DI, `WriteStrategyService`, `WriteBehindService` + `WriteBehindWorker` hosted service, `RefreshAheadService`). Singleton services that need the repository create a scope with `IServiceScopeFactory`.
- Level 7: `StampedeService`, `PenetrationService` (uses `Helper/BloomFilter`), `AvalancheService`, `MultiLevelCacheService` (L1 memory, L2 Redis via `IRedisRepository`, cross-server L1 invalidation over Pub/Sub channel `level7:invalidate`), `MetricsService`.
- `CacheEventLog` publishes the `System.Diagnostics.Metrics` meter `Caching.Academy` (counter `caching_academy.cache_events`, tags `type` and `level`) and keeps totals for the 7.5 dashboard.
- Most demo services are singletons with their own `MemoryCache` instance so lessons do not affect each other; the shared `IMemoryCache` is used by Levels 1 and 3 and by HybridCache's L1.
- Level 2 demos detect cache hits with `IRequestCounter` (`api/level2/counters`): the counter only increases when the controller action really runs.

## Portal lesson page format
The user is a beginner and wants visuals first, little text up front. Every lesson view follows this order:
1. Title and one-sentence lead
2. An animated story: `<div class="story" data-story="N.M"></div>`. Scenes live in `wwwroot/js/stories/levelN.js` as `Stories["N.M"] = { title, height, nodes, links, steps, traces }` and are played by `wwwroot/js/story.js` (Play/Back/Next/Replay, autoplay on scroll, optional speech "Read aloud"). Each step has one short plain-language sentence (`say`) plus actions: `move` (packets, parallel when an array of arrays), `before`/`then` (sequential moves), `flash` (badge), `set` (node subtitle), `hi`, `dim`/`undim`, `clock`, `after`, `rename` (node label), `real` (company banner). Every main story ends with a real-world chapter added in `wwwroot/js/stories/realworld.js` via `addRealWorld(key, company, source, steps)`: nodes are renamed to the company's real parts and a banner names the company and public source.
3. "In the real world": `.rw-grid` of `.rw-card`s (company, headline stat, short story, the lesson, and the public source) showing how big companies (Facebook, Netflix, Amazon, Stack Overflow, PostgreSQL, ...) apply the idea or failed with it. Only use well-documented public facts (papers, engineering blogs, incident reports) and name the source.
4. The long explanation inside `<details class="deep">` ("Read the full explanation"). Inside it, hard concepts get extra mini animations (`<div class="story mini" data-story="N.M-name">` right after the section heading, scenes in `wwwroot/js/stories/deep.js`), and every static `.flow` diagram is animated automatically by `story.js`. Mini animations also end with a real-world step from `realworld.js`.
5. `<h2><span class="try-it">Try it</span>Live demo</h2>`: calls the API, shows results, timings and an event log (`ICacheEventLog`, filtered by key prefix). Where the scene defines `traces`, the demo calls `StoryPlayer.trace("N.M", source)` so the diagram replays the path the real request took.
6. "Experiments: do these in order", then extra theory in a second `details.deep`
7. Key takeaways and common mistakes (`.callout`)
8. "Read the code" list of the files to study, and a link to the next lesson

## Redis
- Connection string key: `ConnectionStrings:Redis`, in StackExchange.Redis format (`host:port,user=...,password=...,abortConnect=false`), not the `redis://` URI format.
- By the user's explicit decision, the Redis Cloud connection string is stored in `src/Caching.Core/appsettings.json` and committed, even though the repository is public. The user knows the risk and will move it to a Render environment variable or user secrets later. Do not move or remove it unless the user asks.
- `RedisConnection` (Infrastructure/Data) owns the one lazy `ConnectionMultiplexer` with `AllowAdmin = true` (needed for INFO and key scans), `AbortOnConnectFail = false` and 2-3 second timeouts. All Redis keys use the prefix `caching-academy:` (`RedisConnection.KeyPrefix`, also the `IDistributedCache` `InstanceName`).
- `AddInfrastructure` registers `RedisConnection`, `IRedisRepository` (direct Redis commands, used by Business) and, when Redis is configured, `IConnectionMultiplexer` plus `AddStackExchangeRedisCache` sharing that connection. Without Redis it registers `AddDistributedMemoryCache` so `IDistributedCache` and `HybridCache` always work.
- `RedisRepository` wraps every Redis error in `CacheUnavailableException`. `Program.cs` has a global exception handler that turns it into HTTP 503 with `{ error }` JSON. Services using `IDistributedCache` catch failures themselves and fall back to the database (a cache must fail open).
- Level 5 services (`RedisPlaygroundService`, `LeaderboardService`, `RateLimiterService`, `PubSubService`, `DistributedLockService`, `RedisInfoService`) call `IRedisRepository` and let `CacheUnavailableException` become a 503; pages show it with `redisErrorHtml`. Redis subscriptions implement `IRedisSubscriber` and are started (and retried every 30 s) by the `RedisSubscriberWorker` hosted service.
- Business `IRedisStatusService` (`GET api/redis/status`) reports configured/connected/ping; portal pages show it with `renderRedisStatus` from `site.js`.
- The Claude cloud sandbox cannot reach the Redis Cloud host. Test Redis code against a local server instead: `apt-get install redis-server`, `redis-server --daemonize yes`, then run the app with `ConnectionStrings__Redis=localhost:6379`.

## Packages
- All Microsoft.* packages (EF Core, Extensions) must stay on version `10.0.x` (currently `10.0.15`). Version 11.x targets net11.0 and does not work on net10.0. Exception: `Microsoft.Extensions.Caching.Hybrid` is versioned separately; `10.11.1` targets net10.0.
- EF Core tools: `dotnet tool install --global dotnet-ef --version 10.0.15`.
- Add a migration: `dotnet ef migrations add <Name> --project src/Caching.Infrastructure --startup-project src/Caching.Core --output-dir Data/Migrations`, then strip the generated comments.

## Running
`dotnet run --project src/Caching.Core` then open `http://localhost:5030` for the portal and `http://localhost:5030/swagger` for the API.

## Deployment
- Hosted on **Render** (free plan) using `Dockerfile` and the `render.yaml` blueprint. GitHub Pages cannot host this app because it needs a .NET server.
- Render builds from the branch named in `render.yaml` and redeploys automatically on every push to it.
- The container listens on port 10000 (`ASPNETCORE_HTTP_PORTS`). Render provides HTTPS.
- The SQLite file is recreated from migrations on each deploy or restart (Render's free disk is temporary). This is fine because the data is only demo data.
- The Redis connection string currently comes from `appsettings.json`. A `ConnectionStrings__Redis` environment variable in Render, if set, overrides it.
